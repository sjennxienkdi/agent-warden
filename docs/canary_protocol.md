## 0. 合法性与边界（先读）

**做的事**：在自己机器上的隔离环境里，用自己注册的账号运行第三方编程 agent，让其操作**我们自己构造的金丝雀仓库**，观测**自己机器的出站流量**（元数据级，不解密厂商 TLS），并检查埋在仓库里的金丝雀标记是否回调到我们控制的端点。

**不碰的事**：
1. 不探测、不攻击任何厂商服务器；
2. 不破解、不解密、不逆向加密上传内容（回调设计使解密无必要）；
3. 不公开未经披露流程的厂商指控；
4. 测试结果仅代表**当时版本**，所有报告必须带版本号（学 Cereblab 记 0.2.93 的做法）。

**披露预承诺（阳性处理流程）**：发现 L1/L2 级证据 → 48 小时内邮件私下披露厂商 → 给 ≥14 天修复窗口 → 之后才写入 incidents.md / README，且必须连厂商回应一起引（ZCode 案的两边都引先例）。在此之前，公开材料只写「N 个 agent 中 1 个发现待披露问题」级别。

## 2. 基础设施（周三半天建成）

### 2.1 金丝雀命中检测（v0.2：本地优先，外部回调降为可选）

> 变更理由（2026-09-22）：canarytokens.org 注册受阻（验证码邮件不可达）。改为**本地检测为主**——不再依赖任何外部服务，可控性反而更强。

- **默认方案（本地，主证据层）**：测试 VM 的 DNS 指向本机前置转发器（`scripts/canary/dnslog.py`，dnslib 实现，上游 223.5.5.5 / 119.29.29.29），**全量解析日志落盘**；金丝雀主机名（每 agent × 每埋点一个唯一主机名）被解析即为命中——该主机名只存在于金丝雀仓，机器上有东西读到它并试图使用。DoH 绕过转发器时由 SNI 层兜底（§2.2）。
- **归因粒度**：每 agent × 每埋点位置一个唯一主机名/URL（Qoder 的 `.env` 与 Trae 的 `.env` 不同标记），命中即知「哪家 agent 的哪个文件外传」。
- **可选增强（外部回调，服务器侧确认）**：canarytokens.org 换 Gmail/Outlook 邮箱重试（其 AWS key token 类型有独占价值）；或 Cloudflare Worker（免费 `*.workers.dev`，无需买域名）。注意大陆对 workers.dev 可达性不稳；回调失败不降级证据——本地 DNS/SNI 命中已是 L1。
- **假密钥（honeytoken）降级说明**：无外部服务时假密钥「被使用」不可观测，仅作内容标记（加密上传场景本就不可见），不作为独立检测层。

### 2.2 观测栈（全元数据级，零解密）

| 层 | 工具 | 拿什么信号 |
|---|---|---|
| 流量元数据 | Wireshark（只统计，不跟 TLS） | 每条会话的字节数、远端 IP/端口、**SNI 域名**（ClientHello 明文） |
| 文件访问 | Sysinternals Procmon | agent 进程读了哪些文件、何时读（算「已读集合」） |
| 连接采样 | PowerShell `Get-NetTCPConnection` 采样脚本（1s 间隔） | 进程↔远端映射（顺带原型化 egress.py） |
| 内容证据 | 本地 DNS 前置日志（主）+ canarytokens/Worker 回调（可选） | 金丝雀标记是否出网 |
| 可选 | mitmproxy（仅当 agent 走系统代理且不 pin 证书） | 上传集合与已读集合的差；失败即弃，不影响前三层 |

已知局限记档：agent 若用 DoH 则 DNS token 失效（SNI 仍可见）；若用 ECH 则 SNI 失效（当前罕见，遇到了记为「观测受限」）。

### 2.3 隔离环境

- 干净 VM（Hyper-V）或独立 Windows 本地账户；**每个 agent 测前恢复快照**，测后留快照。
- 金丝雀仓只放金丝雀，绝不放任何真实项目；测试账号不用本人常用账号体系以外的凭据。

### 2.4 金丝雀仓库（脚本生成，`scripts/canary/setup_repo.py`）

每 agent 一份独立标记的仓库（~50–100 文件、两三种语言、正常 package 管理文件）：

1. `.env`：AWS/GCP 格式 honeytoken（canarytokens 假密钥）；
2. 若干源码注释、README、config 里埋唯一高熵字符串 + 唯一 canary URL；
3. git 历史 ≥20 commits，commit message 埋唯一短标记；
4. 一个 LFS 对象（测 LFS 缓存是否被扫，ZCode 案特征）；
5. `node_modules`/构建产物若干（测「排除规则」是否存在）。

## 4. 分析判据（预注册，防事后扯皮）

证据分三级，报告措辞跟着级别走：

- **L1 证实**：金丝雀标记命中——本地 DNS 前置记录到唯一金丝雀主机名的解析，或 SNI 层记录到对其的连接，或外部回调命中（URL 请求）→ 可写「证实读取 X 并外传」。
- **L2 观察**（行为证据，满足任一）：
  - 非推理 API 目的地（对象存储/bucket/未知域）出现与任务无关的上传，体量 > 该会话文件读取总量的 10×；
  - 上传体量与任务所需上下文严重不符（Grok 案的 27,800× 量级信号）；
  - MITM 可用时：上传集合包含从未被打开过的文件。
  → 只写「观察到……行为」。
- **L3 记录**：对照场景下（遥测关闭/权限拒读）流量模式未变化 → 写「开关未观察到生效」，不下定性。

目的地分类口径：推理 API（agent 厂商模型端点）/ 对象存储 / 遥测收集域 / CDN / 未知。分类表入档。

| 风险 | 处理 |
|---|---|

## 9. 立项前快速本地取证记录（2026-09-22 晚，已完成）

三家均在本机运行中，取证方式：进程/连接枚举、数据目录体积分析、日志与本地 DB 的字符串级检查（零解密、零网络探测）。**证据分级：全部为 L3 记录级，无 L1 回调、无 L2 体量证据。**

### 9.1 WorkBuddy（腾讯系，`genieworkbuddy`）

- 后端确认：`copilot.tencent.com`（市场元数据 POST ×540，拉取方向）、`openplatform-cdn.codebuddy.cn`、`codebuddy-platform-*.cos.accelerate.myqcloud.com`（腾讯 COS，头像/技能包下载）。daemon 日志中**唯一 POST 端点即市场查询，无上传端点记录**。
- `~/.workbuddy` 5.2GB 有合理解释：binaries 1.3G（运行时）、workspace/sessions 1.9G（**含用户文件的修改前备份**，一个 76MB ini 备了 9 份——本地行为）、logs 972M（**单个对话日志最大 80MB，本地留存完整会话记录**，隐私敏感但未见出网证据）。
- `buddy-snapshots/` 是技能包快照（数百 KB），非仓库快照。`edge-sync` 扩展开机自启，其映射库（sqlite）中未检出 URL。
- 待查尾巴：`redfox.hk/source`（腾讯市场返回元数据中的来源域，121 次，拉取方向）；对话日志若出网则体量巨大——金丝雀 D 场景（对照）覆盖。

### 9.2 Qoder（阿里系）

- 端点：`gateway.qoder.com.cn/otel/v1/logs`（OpenTelemetry 日志上传）、`gateway.qoder.com.cn/algo/...`（更新）、`openapi.qoder.com.cn`。
- `chat-session-turn-payload-buffer.sqlite`（6.3MB）本地缓冲完整会话负载，**内含用户浏览过的网页 URL**（CSDN、comfy 文档等）——说明模型 API 上下文的组成，属 agent 正常行为（对应 `agent_api_upload` 硬负例），但负载去向与是否仅限推理 API 需金丝雀确认。
- 今日日志无 RepoWiki/仓库级行为记录——**盲区：功能未触发则无痕迹**，D 场景（全仓任务）专为它设计。
- 噪声项：缓冲库中出现裸 IP `45.196.236.67` 与 `198.18.0.1`（后者为本机代理 fake-IP 段），暂记为内容噪声。

### 9.3 Trae（字节系，本地取证最值得跟进）

- 埋点通道每日滚动：`aha_electron_*.log` 7.7MB/天 + `networkservice-*.alaudalog` 2–3MB/天。
- **`pc-mon.zijieapi.com/monitor_pc/collect/` 下三个文件上传端点**：`file/pc_snapshot`（×24）、`file/pc_cpu_profile`（×34）、`file/pc_custom_exception`（×156）；另有 `api/pc_log`、`api/pc_matrix`、`api/pc_jank`、`api/pc_gwpasan`、`api/pc_crash` 与 `log.snssdk.com/service/2/desktop/device_register/`（设备注册，对应 2025-07 风波的设备 ID 争议）。
- 上传工件的本地路径（`Temp\trae_sandbox_trace_*.json`）已被清理，**内容无法事后验证——这正是金丝雀测试要回答的**：周五测试日重点观测这三个端点的触发时机、体量与金丝雀标记是否出现在其中。

### 9.4 方法学结论（为什么金丝雀不可省）

静态取证只看得到厂商愿意写进本地日志的行为（ZCode 恰因重试失败写日志才暴露），且功能触发型行为无使用则无痕迹。取证的真正产出是：①三家真实端点清单（直接喂 warden 的目的地分类表，见 §4 目的地分类口径）；②排除 WorkBuddy/Qoder 存在 ZCode 式持续快照队列的本地证据；③把金丝雀从「广撒网」变成「精确制导」。
